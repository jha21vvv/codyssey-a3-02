## 📋 항목 1. 기본 기능 동작 및 보고서 충족 여부 (6문항)

### Q1-1. 웹캠 또는 비디오 파일 입력 시 애플리케이션이 에러 없이 시작되고, 화면에 FPS가 실시간으로 표시되는가?
- **답변**:
  - 네. `src/app.py`의 `VideoAnalyzerApp._parse_source()`가 `--source "0"` 같은 숫자 문자열은 웹캠 인덱스 `int(0)`으로, `"data/videos/vtest.avi"` 같은 경로는 파일 경로 문자열로 자동 분기하여 `cv2.VideoCapture`로 엽니다.
  - 매 프레임 `time.perf_counter()`로 직전 프레임과의 경과 시간 `dt = max(now - prev_time, 1e-6)`을 구해 순간 `FPS = 1.0 / dt`를 계산하고, `src/visualizer.py`의 `FrameVisualizer.draw()`가 좌상단 반투명 HUD에 `FPS: 24.5 | Objects: 4` 형태로 실시간 표시합니다.
  - 실행 검증: `python -m src.main --source data/videos/vtest.avi --headless --max-frames 60` 기준 평균 **21.92 FPS**로 에러 없이 동작합니다.

> 💡 **[3개월 차 눈높이 주석]**  
> - **FPS (Frames Per Second)**: "1초에 사진(프레임)을 몇 장 처리하고 있는가"를 뜻하는 속도계입니다. 1장 처리에 `0.05초` 걸렸다면 `1 / 0.05 = 20 FPS`가 됩니다.  
> - **`max(..., 1e-6)`을 넣은 이유**: 컴퓨터가 너무 빨라서 시간 차이 `dt`가 `0`이 되면 `1 / 0` 에러(`ZeroDivisionError`)가 터지므로, 아주 작은 수(`0.000001`)를 하한으로 깔아두는 안전장치입니다.

  - `src/visualizer.py`가 ID별 고유 색상 팔레트(`color_for_id`)로 사각형(`cv2.rectangle`), `ID #N` 텍스트(`cv2.putText`), 이동 경로 폴리라인(`cv2.polylines`)을 프레임 위에 렌더링합니다.

> 💡 **[3개월 차 눈높이 주석]**  
> - **바운딩 박스(Bounding Box)**: 움직이는 물체를 딱 맞게 감싸는 네모 상자입니다.  
> - **궤적(Trajectory)**: 객체의 배꼽(중심점) 좌표들을 최근 50프레임 동안 모아 실로 꿰듯 선으로 이은 발자국 표시입니다.

### Q1-3. 키보드 입력(`q`: 종료, `s`: 스냅샷 저장, `p`: 일시정지)이 정상적으로 동작하고, 입력 없는 상태에서도 애플리케이션이 안정적으로 유지되는가?
- **답변**:
  - 네. `src/app.py`의 `run()` 루프에서 `key = cv2.waitKey(1 if not paused else 30) & 0xFF`로 키 입력을 감지합니다.
    - `q` 또는 `ESC(27)`: `break` 후 `finally:`에서 `cap.release()`와 `cv2.destroyAllWindows()`로 리소스 안전 해제
    - `p`: `paused = not paused` 토글 (일시정지 중에는 `PAUSED` 배지 표시 및 `waitKey(30)`으로 CPU 과부하 방지)
    - `s`: `FrameVisualizer.save_snapshot()`으로 `output/snapshots/snapshot_YYYYMMDD_HHMMSS_f00000.png` 저장 (Windows 한글 경로 깨짐 방지를 위해 `cv2.imencode` + `Path.write_bytes` 사용)
  - 키 입력이 없을 때는 `waitKey`가 `-1`을 반환하므로 아무 분기에도 걸리지 않고 안정적으로 다음 프레임을 계속 처리합니다. (`tests/test_app_and_constraints.py`의 `test_keyboard_controls_pause_snapshot_quit`에서 Mock으로 자동 검증 완료)

> 💡 **[3개월 차 눈높이 주석]**  
> - **`& 0xFF`는 왜 붙이나요?**: 64비트 OS에서 `cv2.waitKey()`가 돌려주는 숫자 앞부분에 불필요한 비트가 붙을 수 있어, 맨 뒤 8비트(순수 키보드 아스키 코드)만 잘라내기 위한 마스킹 기법입니다.  
> - **`try-finally`의 역할**: 도중에 에러가 나거나 강제 종료해도 카메라 전원을 반드시 끄고 나가게 하는 안전벨트입니다.

## 🏗️ 항목 2. 아키텍처 설계 및 모듈 분리 (4문항)

### Q2-1. `Tracker` 클래스를 별도 파일(`tracker.py`)로 분리한 구조를 보여주고, 이 클래스가 메인 루프와 어떻게 역할을 분담하는지 설명할 수 있는가?
- **답변**:
  - `Tracker` 클래스는 독립 파일 **`src/tracker.py`**에 완전히 분리되어 있으며, 메인 루프(`src/app.py`의 `VideoAnalyzerApp`)와는 **명확한 데이터 계약(`List[Detection]` → `Dict[int, TrackedObject]`)**으로만 통신합니다.
  - **역할 분담**:
    - **메인 루프 (`src/app.py`)**: 영상 읽기(`VideoCapture`), FPS 측정, 키보드 제어(`q`/`s`/`p`), 하위 모듈 순서 호출, 리소스 해제(`try-finally`)만 담당. (ID가 어떻게 부여되는지 내부를 전혀 모름)
    - **추적기 (`src/tracker.py`)**: 감지된 좌표 목록(`detections`)만 입력받아 유클리드 거리 계산, 1:1 매칭, 신규 ID 발급(`register`), 미등장 ID 삭제(`deregister`), 궤적(`deque`)·속도 갱신만 전담.
  - 덕분에 `Tracker`는 영상 파일이나 OpenCV 없이도 순수 좌표만으로 단위 테스트(`tests/test_tracker.py`)가 0.01초 만에 가능합니다.

> 💡 **[3개월 차 눈높이 주석]**  
> - 식당으로 비유하면 `app.py`는 **매장 매니저**, `tracker.py`는 **번호표 관리 전담 직원**입니다. 매니저는 "지금 손님 좌표 목록 여기 있어요"라고 넘기기만 하고, 번호표를 이어줄지 새로 뽑을지는 전담 직원이 알아서 처리해 결과를 돌려줍니다.

### Q2-2. 배경 차분, 객체 감지, 추적 로직, 특징점 매칭 등 각 기능을 어떤 기준으로 함수 또는 모듈로 분리했는지, 그 설계 의도를 코드를 보며 설명할 수 있는가?
- **답변**:
  - **단일 책임 원칙(SRP: 변경 이유가 다른 코드는 다른 파일로 분리)**을 기준으로 파이프라인 1단계 = 1모듈로 분리했습니다.
    1. `src/background.py` (`BackgroundSubtractor`): **"배경과 전경을 어떻게 분리할 것인가?"** (MOG2 ↔ `absdiff` 교체 시 이 파일만 수정)
    2. `src/detector.py` (`MotionDetector`): **"전경 마스크에서 어떤 덩어리를 객체로 인정할 것인가?"** (윤곽선·면적 필터링 전담)
    3. `src/tracker.py` (`Tracker`): **"프레임 간 같은 객체에 어떻게 ID를 유지할 것인가?"** (거리 행렬·ID 수명·궤적 전담)
    4. `src/feature_matcher.py` (`FeatureMatcher`): **"등록된 특정 물체를 어떻게 재인식할 것인가?"** (ORB ↔ SIFT 교체 시 이 파일만 수정)
    5. `src/visualizer.py` (`FrameVisualizer`): **"결과를 화면에 어떻게 그릴 것인가?"** (UI·HUD·스냅샷 전담)
    6. `src/config.py` (`AppConfig`) & `src/main.py`: 설정 검증 및 CLI 진입점.

> 💡 **[3개월 차 눈높이 주석]**  
> - 이렇게 레고 블록처럼 쪼개놓으면 나중에 MOG2를 다른 배경 모델로 바꾸거나, ORB를 SIFT로 바꾸거나, 심지어 고전 추적기를 딥러닝(DeepSORT)으로 업그레이드할 때도 **해당 파일 1개만 갈아 끼우면 나머지 코드는 한 줄도 안 건드려도 됩니다!**

### Q2-3. 학습률, 면적 임계값, 거리 임계값, 사라지는 프레임 수 등의 파라미터를 어디에 어떻게 분리해서 관리하고 있는지, 왜 그렇게 설계했는지 설명할 수 있는가?
- **답변**:
  - 모든 하이퍼파라미터를 **`src/config.py`의 불변 데이터클래스 `@dataclass(frozen=True) class AppConfig`** 한곳에 중앙 집중 관리하며, `src/main.py`의 `argparse` CLI 옵션으로 외부 주입받습니다.
  - **설계 의도 3가지**:
    1. **하드코딩 제거**: 코드 여러 군데에 `500`, `0.005`, `80.0` 같은 매직 넘버가 흩어져 있으면 실험할 때마다 파일을 뒤져야 합니다.
    2. **사전 유효성 검증 (`__post_init__`)**: `learning_rate` 범위, 홀수 `morph_kernel_size`, `min_area <= max_area` 등을 앱 시작 전에 즉시 검사해 잘못된 설정으로 인한 런타임 버그를 원천 차단합니다.
    3. **불변성(`frozen=True`)**: 실행 도중 어느 모듈도 설정값을 실수로 덮어쓰지 못하도록 보장합니다.

> 💡 **[3개월 차 눈높이 주석]**  
> - `frozen=True`는 설정표를 **코팅**해 두는 것과 같습니다. 처음에 `AppConfig`를 만들 때 딱 1번 검증을 통과하면, 그 뒤로 프로그램이 끝날 때까지 아무도 숫자를 몰래 바꿀 수 없습니다.

### Q2-4. 테스트 영상을 변경하거나 새로운 환경에서 실행할 때, 코드의 어떤 부분을 수정해야 하는지 설명할 수 있는가?
- **답변**:
  - **코드를 단 한 줄도 수정할 필요가 없습니다!** 모든 환경 변수를 CLI 인자로 노출해 두었습니다(`src/main.py`).
  - 예시:
    - 영상/웹캠 변경: `--source data/videos/people-detection.mp4` 또는 `--source 0`
    - 원거리/소형 객체 환경: `--min-area 200 --max-distance 50`
    - 조명 변화가 잦은 로비/출입구: `--learning-rate 0.01 --max-disappeared 20`
    - 재인식 타겟 변경 또는 정밀 모드: `--target my_object.png --feature-method sift`

### Q3-2. 이전 프레임과 현재 프레임의 객체 간 거리 행렬을 계산하여 ID를 매칭하는 로직이 코드에서 어떻게 구현되어 있는지, 해당 코드를 지목하며 설명할 수 있는가?
- **답변**:
  - **`src/tracker.py`의 `Tracker.update()` 메서드**에 구현되어 있습니다:
    1. **거리 계산**: 현재 활성 `object_ids = sorted(self.objects.keys())`와 현재 프레임 `detections`의 모든 조합에 대해 `self._euclidean_distance(ref_pt, det.centroid)`(`math.hypot` 기반 $\sqrt{\Delta x^2 + \Delta y^2}$)를 계산해 `(dist, obj_id, det_idx)` 튜플 리스트 `pairs`를 생성합니다.
    2. **결정론적 정렬**: `pairs.sort(key=lambda item: (item[0], item[1], item[2]))`로 거리가 짧은 순(동률 시 낮은 `obj_id` 우선)으로 정렬합니다.
    3. **탐욕 1:1 매칭**: 정렬된 `pairs`를 순회하며 `dist > self.max_distance`이면 즉시 `break`하고, `used_object_ids` / `used_det_indices` 집합에 없는 쌍만 확정해 속도(`vx, vy`), 중심점, 바운딩 박스, `disappeared = 0`, 궤적(`trajectory.append`)을 갱신합니다.

> 💡 **[3개월 차 눈높이 주석]**  
> - 모든 기존 손님(M명)과 새 위치(N개) 사이의 거리를 줄자(`math.hypot`)로 전부 재어 표(`pairs`)에 적은 뒤, **가장 짧은 거리 커플부터 1:1로 짝을 짓되, 80px(`max_distance`)을 넘으면 중단**하는 구조입니다.

### Q3-3. `Tracker` 클래스 내부에서 "사라진 객체"와 "새로 등장한 객체"를 어떤 기준으로 구분하도록 설계했는지, 왜 그 기준을 선택했는지 설명할 수 있는가?
- **답변**:
  - **`src/tracker.py`의 `Tracker.update()` 후반부**에서 `used_object_ids`와 `used_det_indices` 집합의 차집합으로 명확히 구분합니다:
    - **사라진 객체 (`obj_id not in used_object_ids`)**: 매칭에 실패한 기존 객체는 즉시 삭제하지 않고 `disappeared += 1`을 누적하다가 **`disappeared > self.max_disappeared` (기본 15프레임)**를 초과할 때만 `deregister(obj_id)`로 삭제합니다.
      - *선택 이유*: 기둥 가림이나 1~3프레임짜리 일시적 배경 차분 누락으로 인해 같은 사람에게 매번 새 ID가 발급되는(ID 분절) 현상을 막기 위함입니다.
    - **새로 등장한 객체 (`det_idx not in used_det_indices`)**: 기존 어떤 객체와도 `max_distance`(80px) 이내로 매칭되지 못한 신규 감지는 `register(det)`로 새 ID(`next_object_id`)를 부여합니다.
      - *선택 이유*: 1프레임 사이에 정상 보행자가 이동할 수 없는 거리(`> 80px`)에서 나타난 객체는 기존 객체의 이동이 아니라 화면에 새로 진입한 별개 객체이기 때문입니다.

### Q4-5. 이번 미션에서 경험한 한계들을 바탕으로, 딥러닝 기반 접근(예: 객체 탐지 학습, 데이터 기반 특징, 환경 학습)이 이러한 문제를 어떻게 완화할 수 있는지, 본인의 실험 결과와 연결하여 설명하라.
- **답변**:
  1. **객체 탐지 학습 (YOLO / RT-DETR) → 정지 실패(100%) & 조명 붕괴(80%) 해결**:
     - 배경 차분은 "이전 프레임과 픽셀이 다른가?"만 보므로 사람이 멈추거나(5/5 실패) 조명이 `+65` 변하면(4/5 실패) 즉시 무너집니다. 반면 딥러닝 탐지기는 단일 프레임에서 **"이 영역이 사람인가?"**를 의미론적으로 직접 판별하므로 정지·조명 급변·그림자에서도 안정적으로 객체를 검출합니다.
  2. **외형 임베딩 기반 추적 (DeepSORT / Re-ID) → 겹침 ID Switch(70% / 속도규칙 30%) 해결**:
     - 위치·속도 규칙만으로는 교차 후 방향 전환 시(Case 05·06·08) 100% ID가 바뀌었습니다. CNN 기반 Re-ID 네트워크가 각 객체의 옷·체형 특징 벡터를 추출해 코사인 유사도로 매칭하면, 겹쳤다 떨어져도 원래 ID를 복원할 수 있습니다.
  3. **데이터 증강 기반 학습 특징 (SuperPoint / ViT) → 회전·가림 매칭률 급락(ORB 4.86%, SIFT 13.25%) 해결**:
     - 수많은 회전·가림·3D 시점·조명 변형 데이터를 학습한 신경망은 국소 코너가 가려져도 객체의 전역적·의미론적 구조로 동일 물체를 인식하여 일반화 성능을 획기적으로 높입니다.
